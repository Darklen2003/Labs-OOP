## Контекст
В исходной версии проекта сущности представляли собой несвязанные классы с неявными интерфейсами. Проверки возможностей объектов выполнялись через `hasattr` или проверку конкретных типов, числовые параметры баланса были захардкожены в методах как магические числа, а логирование велось через прямые вызовы `print()`. Это затрудняло масштабирование кодовой базы, тестирование и добавление новых игровых механик.

## Решение
1. Ввести абстрактный базовый класс `GameObject` (`abc.ABC`) для объединения жизненного цикла сущностей (автоинкремент `id`, флаг `active`, метод `deactivate()`, абстрактные `update()` и `draw()`).
2. Выделить отдельные способности в структурные интерфейсы `typing.Protocol` (`Movable`, `Drawable`, `Collidable`) с аннотацией `@runtime_checkable`.
3. Вынести числовые константы в неизменяемые конфигурации (`@dataclass(frozen=True)`).
4. Реализовать `LoggingMixin` с `__slots__ = ()` для централизованного вывода через стандартную библиотеку `logging`.

## Рассмотренные альтернативы
1. **Глубокая иерархия классов (наследование от `MovableObject`, `StaticObject`):**
   - *Отклонено:* приводит к комбинаторному взрыву классов и жёсткой связанности.
2. **Использование только `Protocol` без базового класса:**
   - *Отклонено:* протоколы не позволяют хранить общее состояние и реализацию базовой логики идентификаторов (`_next_id`, `_id`, `_active`).
3. **Комбинация `ABC GameObject` + `Protocol` + `LoggingMixin`:**
   - *Выбранное решение:* разделяет сущность («чем объект является») и способности («что объект умеет делать»), исключая дублирование кода.

## Последствия
- ✅ Единый контракт жизненного цикла для всех объектов игрового мира.
- ✅ Полиморфная проверка контрактов через `isinstance(obj, Protocol)` во время выполнения.
- ✅ Изоляция параметров баланса в DTO-конфигурациях без правки логики классов.
- ✅ Разделение технического вывода логов и отрисовки игрового интерфейса.
- ⚠️ Необходимость соблюдать порядок в MRO при множественном наследовании (миксин объявляется первым).
