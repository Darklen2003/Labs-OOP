## 1.2. Выявленные проблемы и план рефакторинга

### 1. Какие классы должны наследоваться от `GameObject`? Почему?
От базового класса `GameObject` должны наследоваться классы **`Player`**, **`Monster`**, **`Chest`** и **`Trap`**.

**Обоснование:**
- Все они представляют собой материальные объекты игрового мира, обладающие координатами, временем жизни и уникальным идентификатором.
- Для них требуется единый жизненный цикл: они должны обновлять внутреннее состояние (`update(dt)`), возвращать строковое представление для отображения (`draw()`) и корректно удаляться из мира при гибели или сборе через единый метод `deactivate()`.
- Контейнеры и управляющие классы (`Room`, `Game`) не должны наследоваться от `GameObject`, так как они управляют сущностями и игровым циклом, а не являются объектами на игровом поле.

### 2. Какие способности нужно выделить в протоколы?
Необходимо выделить 3 ключевых структурных интерфейса (`typing.Protocol`):

1. **`Movable`**: способность сущности менять свои координаты (`move(dx: float, dy: float) -> None`).
   - *Реализуют:* `Player`, `Monster`.
   - *Не реализуют:* статичные объекты вроде `Chest` и `Trap`.
2. **`Drawable`**: способность предоставлять графический глиф/символ для отображения на карте (`draw() -> str`).
   - *Реализуют:* все видимые сущности (`Player`, `Monster`, `Chest`, `Trap`).
3. **`Collidable`**: способность участвовать в проверке пространственных коллизий (свойство `collision_radius: float` и метод `collides_with(other: Any) -> bool`).
   - *Реализуют:* все объекты, с которыми игрок или монстры могут столкнуться на сетке.

### 3. Какие значения должны стать конфигурациями?
Все разрозненные числовые литералы выносятся в неизменяемые `@dataclass(frozen=True)`:

* **`GameConfig`**:
  - `field_width: int = 20` (ширина игрового поля);
  - `field_height: int = 10` (высота игрового поля);
  - `max_turns: int = 100` (максимальное количество ходов);
  - `step_energy_cost: int = 1` (расход энергии на один шаг).
* **`PlayerConfig`**:
  - `max_hp: int = 100` (максимальный запас здоровья);
  - `max_energy: int = 25` (максимальный запас энергии);
  - `base_attack: int = 12` (базовый урон героя);
  - `collision_radius: float = 0.5` (радиус коллизии).
* **`MonsterConfig`**:
  - `max_hp: int = 40`;
  - `attack_power: int = 8`;
  - `aggro_radius: float = 4.0` (дистанция обнаружения игрока);
  - `collision_radius: float = 0.5`.
* **`RoomConfig`** (изменяемый dataclass):
  - `monsters: list[MonsterConfig] = field(default_factory=list)` (список монстров для генерации);
  - `chest_count: int = 2` (количество сундуков);
  - `trap_count: int = 3` (количество ловушек).

### 4. Какие классы должны получить логирование через миксин?
Классы **`Player`**, **`Monster`** и **`Game`** должны наследовать `LoggingMixin`.

**Обоснование:**
- В `Player` и `Monster` миксин логирует ключевые доменные события: получение урона, перемещение, атака, деактивация (смерть).
- В `Game` миксин фиксирует служебные события цикла: старт игры, смена ходов, завершение партии, обнаружение коллизий.
- Использование миксина позволит убрать хардкод `print()` и централизованно маршрутизировать логи через стандартную библиотеку `logging` с именем конкретного класса (`[Player] INFO: ...`).

## 2.1 Ответы на вопросы

### 1. Почему `GameObject` — это ABC, а не Protocol?
* **Семантика отношения («is-a»):** `GameObject` задает базовую сущность игрового мира (чем объект является), а не отдельную отчуждаемую роль или способность[cite: 1].
* **Наличие состояния и базовой реализации:** `GameObject` инкапсулирует общий жизненный цикл и разделяемое состояние: генератор уникальных идентификаторов `_next_id`, приватные поля `_id`, `_name`, `_active`, свойства только для чтения и метод `deactivate()`[cite: 1]. Протоколы в Python не предназначены для хранения разделяемого состояния базового класса[cite: 1].
* **Строгий контракт на уровне рантайма:** Механизм `abc.ABC` запрещает создание экземпляра самого базового класса и гарантирует выброс `TypeError`, если в подклассе не реализованы обязательные абстрактные методы `update()` и `draw()`[cite: 1].

### 2. Почему `Movable` — это Protocol, а не ABC?
* **Семантика поведения («can-do»):** `Movable` описывает конкретное действие (что объект умеет делать — перемещаться в координатной сетке), а не тип сущности[cite: 1].
* **Слабая связанность и отсутствие жесткого наследования:** Способность двигаться может требоваться разнородным объектам (герой, монстр, снаряд, летающий питомец)[cite: 1]. Протокол исключает необходимость выстраивать глубокую иерархию классов или искусственный промежуточный класс `MovableObject`, предотвращая проблемы множественного наследования[cite: 1].
* **Структурная типизация:** С декоратором `@runtime_checkable` подсистема движения может проверять контракт через `isinstance(obj, Movable)` без привязки к конкретному предку в дереве классов[cite: 1].

### 3. Какие ваши классы реализуют несколько протоколов одновременно? Почему?
* **`Player` и `Monster` реализуют `Movable`, `Drawable` и `Collidable` одновременно**[cite: 1]:
  * Они динамически меняют координаты на игровом поле (`Movable`)[cite: 1].
  * Они возвращают текстовый символ для отображения на сетке (`Drawable`)[cite: 1].
  * Они обладают радиусом коллизии и участвуют в расчете столкновений с другими объектами (`Collidable`)[cite: 1].
* **`Chest` и `Trap` реализуют `Drawable` и `Collidable` одновременно**[cite: 1]:
  * Это статичные объекты окружения: они отрисовываются на карте (`Drawable`) и взаимодействуют с персонажами при контакте (`Collidable`), но не обладают логикой самостоятельного движения (`Movable` не реализуется)[cite: 1].

### 4. Есть ли класс, который не должен наследоваться от `GameObject`? Обоснуйте.
Классы **`Game`** (оркестратор игрового цикла), **`Room`** (контейнер объектов/уровень), конфигурационные датаклассы (**`GameConfig`**, **`PlayerConfig`**) и **`LoggingMixin`** не должны наследоваться от `GameObject`[cite: 1].

* **Отсутствие материальной природы в игровом мире:** Ни одна из этих сущностей не является физическим объектом на координатной сетке: они не имеют координат, не отрисовываются в ячейках (`draw()`) и не требуют обновления состояния кадра (`update()`) в общем списке сущностей[cite: 1].
* **Соблюдение LSP и чистоты интерфейса:** `Game` управляет процессом, `Room` хранит коллекции, а датаклассы представляют собой DTO[cite: 1]. Наследование их от `GameObject` вынудило бы реализовывать бессмысленные методы-заглушки для `update()` и `draw()`, нарушая принцип подстановки Лисков[cite: 1].
